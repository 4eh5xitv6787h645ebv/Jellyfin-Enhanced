### 45, 47, 48. Versioned docs with mike

Housekeeping, applied as is, one commit each in upstream's order: `git show <sha> | git apply --3way` applied cleanly
each time, and afterwards `.github/workflows/docs.yml`, `.github/docs/requirements.in` and
`.github/docs/requirements.txt` are byte-identical to upstream's at that commit. `mkdocs.yml` gains upstream's
`extra.version` block (provider `mike`, default `latest`) and keeps this tree's own `exclude_docs` line for
`upstream-sync*`, the one difference it already had.

What the three commits do together: the docs workflow stops uploading a Pages artifact and publishes with mike to the
`gh-pages` branch. A push to `main` publishes `dev`, titled "main" in the version picker. A tag push, or a manual run
with `release` set, publishes that release as `major.minor`, titled "latest (12.15)", moves the `latest` alias and the
site default to it, and gives the release it replaces its plain title back. A manual run can also build an older tag
or branch (`ref`) without moving `latest` (`latest` off), which back fills released versions; the tooling then still
comes from `main`'s hash-pinned requirements, the npm and flag-group steps are skipped where the built ref lacks them,
and a ref whose `mkdocs.yml` has no mike provider is built with an extra config that inherits it and adds the
switcher. Only the deploy job may write to the repository; the workflow's default token is read-only, and the unused
cache step goes.

Nothing the plugin ships changes, and this tree is never pushed, so the workflow only runs where upstream's does. No
difference from upstream.

### 73. The Elsewhere custom branding icon: explained, checked, and uploadable

What upstream changed. Administrators can upload the icon (PNG, JPEG, GIF, WebP or SVG) in the Custom Branding group
instead of hosting it. It is a sixth branding slot, `elsewhere-icon.png`, checked on upload by type and by content (the
first 64 KB must be a recognisable image; an empty file is refused), and served to everyone by the anonymous
`GET /JellyfinEnhanced/ElsewhereBrandingIcon`, typed by content, with a sandboxing CSP and `nosniff` (the admin preview
too). Public config carries `ElsewhereCustomBrandingIconVersion` (last-write ticks and size, empty without an upload),
which makes the panel use the upload with `?v=<version>`. Icon paths under `/web/` and `/JellyfinEnhanced/` resolve
through ApiClient, so they work under a base path; the icon is centred against the message (the title's `cssText` reset
dropped it); a failed icon logs why. The admin page explains what the URL must be, test-loads it and warns under the
field when a browser cannot load it (naming a server file path as such), skips that check while an icon is uploaded,
Elsewhere is off or there is no message, checks dropped files against the slot's types, and shows the server's reason
for a refused upload without its JSON quoting.

Where it lives here (the ledger's `notes` list every difference):

- Server: the branding routes in `Features/Chrome/JeChromeController.cs`; the slot's rules (name, types, sniffing,
  version) in a new stateless `Shared/Branding/ElsewhereBrandingIcon.cs`, because Platform's public config needs the
  version and a controller may not reach another feature; the field in `Transport/BootstrapConfig.cs`, so
  `/public-config`, `/bootstrap` and the generated contracts carry it.
- Client: `features/details-providers/elsewhere-branding.ts` (new; it keeps `elsewhere.ts` under its size ratchet,
  lowered from 970 to 961 lines) and the centring in `elsewhere.ts`; the admin slot and warning in
  `admin/config/sections/elsewhere.ts`, the upload rules, error text and URL check in `admin/config/page/branding.ts`,
  re-checked from `gated-help.ts` on every dependency update as upstream does.
- Not ported because already present: upstream's switch from template literals to concatenation in the config page
  (the dashboard reads `${…}` there as translation keys). The rewrite's HTML build already rewrites `${`
  (`scripts/client/html-entries.mjs`); the generated `configPage.html` holds none.
- Records: `config-flag-groups.json` regenerated (`ElsewhereIconInput`, as upstream); the production inventory
  regenerated; `api.md`'s route count 221 → 222; the eight new control ids in `tests/fixtures/admin-config-baseline.json`;
  `Shared/Branding` in `project-structure.md`.

### 74. The MDBList ratings list on the Services tab

The Services tab shows a linked copy of the MDBList card. The engine's markup copy of "Configure ratings shown" lost the
ticks (a checkbox's `checked` property is not markup), its arrows did nothing, and its edits never reached Save. As
upstream, both lists are now built by the page (`page/display-cards.ts`) and kept in step both ways, on a tick and on an
arrow; Save still reads the card's list. "Configure ratings shown" is a group like its neighbours. That intentional
schema change removes the old `<details>` wrapper's two ids (`mdblistSourcesAdminDetails` and its `--mirror`; no code
read them) from the `renderedIds` record in `tests/fixtures/admin-config-baseline.json`; no control, setting or section
id changes (`docs/rewrite/admin-config.md`: regenerate the record only for an intentional schema change).

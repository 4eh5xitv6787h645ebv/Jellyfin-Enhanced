## 2. The entries

### 81 and 82. Analytics icon on reported settings; the page address keeps the tab and card

Upstream adds an administrator-only `GET usage/fields` that lists the configuration properties its usage report
carries, and the configuration page puts an `insights` icon (a link to the Usage Statistics card) on each such setting.
The page's address now names the tab and card shown (`tab=`, `card=`; `jeSection=media-tags` with the Media Tags
section in `tab=`), so a reload or a shared link returns there. 82 is upstream's bot regenerating its inventory for the
new route.

Ported as behaviour (the ledger notes have every detail):

- **Server.** The route sits in the platform feature's controller (`Features/Platform/JePlatformController.cs`,
  `GetUsageReportedFields`), `[Authorize]` and refused unless `IsAdminUser()`, as upstream.
  `AnalyticsReportingService.GetReportedSettingNames` uses upstream's `IsReportedFlag`, which the report's flag list now
  shares. **Difference:** the settings the report sends in a reduced shape are one named list and include
  `LanguageTagsPriority`, which the report carries (codes only) and upstream's list leaves out. On the lab, upstream's
  route answers 319 names and this one 320; the page draws that setting on the Media Tags tab, which has no icons, so the
  page shows the same 228 icons on the same settings as upstream's build.
- **Client.** The engine (`window.JEAdmin`) gains `setHash`/`slugOf` (`engine/address.ts`), `openCard` and
  `markAnalytics`; `activateTab`, the deep-link reader and the page start do the rest. **Differences from upstream**:
  1. Upstream restores the tab kept in the session before it reads the address, and that restore now rewrites the
     address, so the link that opened the page is lost: with another tab saved in the session, a reload of or a link to
     `jeSection=media-tags&tab=…` or `jeSection=<setting>` opens the saved tab (lab rows H, I and K below, upstream's
     build). The rewrite reads the address the page opened at.
  2. `openCard` looks only at the cards of the tab the address names; upstream takes the first card of that name on any
     tab.
  3. A group in the sidebar writes its card too; the address writes only this page's own address, skip writes that
     change nothing and keep the router's history state; the Media Tags section is written only while that tab is shown,
     and the listener goes with the view.
- **Tests that failed first** (`p81.tests.txt`): `admin-config-address.test.mjs` (4 of its 5 failed with no port; the
  fifth, no icon on a failed read, is a guard), the Media Tags address test, and the backend name list test, which
  failed against upstream's list verbatim on `LanguageTagsPriority`. The client port in upstream's order failed all three
  session guards (`@956b0419`); the port passes them.
- **Two existing tests restated, not loosened.** "Links to the page itself open in place" and "What's New … with a link
  to their tab" took "the address did not change" as their proof that a link did not navigate. The upstream change makes
  the address change on purpose (by `history.replaceState`, which is not a navigation). They now assert what they meant:
  no `hashchange` fired and no history entry was added. A followed link does both; this was checked in jsdom first. They
  also check that the address names what is shown.

## Where the third wait comes from (a temporary log line in the test, run alone, then removed)
idle waits as [ms since boot start, last module run, modules run so far]:
DIAG [[5,null,0],[6,null,0],[39,"enhanced/config.js",3]]
The first two are the planned ones (before the request, before the modules). The third is runBundleModules
(client/src/bootstrap/loader/component-loader.ts) ending its slice because its 10 ms run budget
(BUNDLE_RUN_BUDGET_MS) was spent on the wall clock: core/navigation.js, core/session.js and the real
enhanced/config.js (152 KB) took about 33 ms in a cold realm. The loader behaves as designed; the test counted a
wall-clock-dependent wait.

## The fix (test only; the expected counts are unchanged)
Both tests in the file that count idle waits stop the realm's clock (boot.window.performance.now = () => 0), as
tests/frontend/bootstrap/bootstrap-loader-rewrite.test.mjs's slicing test already does since ee0ff7c0. A loader that
waited once per group would still be caught: each run of runBundleModules begins with its own wait, whatever the clock.

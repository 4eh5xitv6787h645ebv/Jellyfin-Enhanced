## 2. The entry

### 68. Reclaimerr beside Maintainerr, and a Leaving Soon page

What upstream added. Reclaimerr can feed the Leaving soon badge, the Leaving soon home row and the item menu in place
of Maintainerr; exactly one of the two is on (a Use switch on each card; the save keeps the one switched on last). The
server reads Reclaimerr's cleanup candidates with its API token and, with a service account, its scheduled manual
deletions (a whole title or one movie file; a scheduled file marks the library item holding it, and the primary item
when it is a hidden alternate version). In the item menu administrators keep, mark and change the date (Reclaimerr
takes an exact day; a movie kept in several versions is scheduled by the picked version only, and nothing is scheduled
when Reclaimerr cannot confirm the version), and anyone signed in can request a removal, filed as a Reclaimerr
deletion request (asking twice says it is already waiting). Requests and schedules carry the Jellyfin user's name
through Reclaimerr's trusted-proxy sign-in, with the service account as the fallback, and a Create service account
button makes one. The Leaving Soon page lists what is leaving that the user can see, with days left; administrators
keep or change dates there and approve (after a confirmation: Reclaimerr deletes on approval) or deny requests; other
users see their own. It is a native Home tab, a Custom Tabs panel or a Plugin Pages page.

Where it lives here (the ledger's `notes` list every difference):

- Server: `Features/MediaTags/Services/ReclaimerrActions.cs` and `ReclaimerrSession.cs` (upstream's files in this
  tree's namespace); `LeavingSoonService`, `MaintainerrHttp`, `MaintainerrActions`, `TagCacheLeaving` as upstream; the
  source rules in `Shared/MediaTags/LeavingSoonSources.cs`; the routes as partials of the feature's one controller,
  `JeMediaTagsController.Reclaimerr.cs` and `JeMediaTagsController.LeavingSoon.cs` (same paths, verbs and checks as
  upstream's `ReclaimerrController` and `LeavingSoonController`); the bootstrap fields in `Transport/BootstrapConfig.cs`.
- Client: the item menu in `features/media-tags/editor/maintainerr-item-menu.ts`; the page and its tab in
  `features/media-tags/leaving-soon/`, shipped inside `js/tags/tag-item-menu.js` (the load order and output keys are
  pinned, so no new script); the Plugin Pages page `PluginPages/LeavingSoonPage.html` from
  `client/html/bootstrap-pages/LeavingSoonPage.html` and `client/src/pages/leaving-soon-page.ts`; the admin page's
  cards in `admin/config/sections/arr.ts`, `pages.ts` and `about.ts`, wired in `page/service-status.ts`.
- Two guard rules shaped the client code: the tab follows the shared navigation hook instead of its own `hashchange`
  listener (leak guard L2), and the page's five-minute refresh is a data poll that looks up no element (performance
  rule R5); a page host that left the document stops it at the next navigation.

Not changed, noted: the shared client that talks to Maintainerr and Reclaimerr keeps cookies, so after a local-login
fallback the service account's session cookie also rides on later Reclaimerr requests, including the ones meant to act
as a user (upstream has the same). A cookie-free client would change an existing service-factory contract line, so it
is filed for a person (`je12 found-bug`, NEW-20261117-173638).

### 69. Season and episode pages show their series' Similar and Recommended rows

Seerr knows TV media only by the series' TMDB ID, so a season or episode page had no rows. The rows now load the
season's or episode's series as the current user (`SeriesId`; a season may fall back to `ParentId`) and use its TMDB
ID; no series, no series TMDB ID or no access to it gives no rows and no request, and Request More still only looks at
the item itself, so it stays on series pages. The rewrite's
`client/src/features/seerr/details/details-page/item-details-entry.ts` had upstream's old logic; it now has the new
logic (`getParentSeries`, `getTmdbIdFromItem`'s `viaSeries`, passed by the rows only). Upstream's tests
(`pages-seerr-details-rows.test.mjs`, identical here before) and docs apply as is. No difference from upstream.

### 70. The bookmark marker after deleting the last bookmark: already present

Upstream's `createBookmarkMarkers()` returned on an empty list before it removed the markers already drawn, so deleting
the only bookmark left its marker on the seek bar. This tree's `createBookmarkMarkers` (`client/src/features/bookmarks/
bookmarks.ts`) removes the slider's markers first and has no such early return. Upstream's test, added unchanged,
passes here and fails when upstream's old early return is put back (`p70.tests.txt`); it stays as a guard.

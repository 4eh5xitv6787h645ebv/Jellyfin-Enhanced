## 2. Why 120 is deferred

Upstream's approve route (`POST arr/requests/{requestId}/approve` and `/decline`, one action `ActOnRequest`) now
takes an optional body: it reads the request from Seerr, edits it (`PUT`) and then approves, and it refuses a change
of who the request is for unless the caller is a Jellyfin administrator. Those are new administrator checks in an
existing route, so three existing contract lines change:

- `auth-helper-calls.snapshot.json`, `ActOnRequest`: `{"IsAdminUser":2,"User":1,"UserHelper.GetCurrentUserId":1}`
  becomes `{"IsAdminUser":5,…}`;
- `auth-reads-by-route.base.json`, `POST …/approve` and `POST …/decline`: the same change.

The manager check moves into `ResolveRequestManagerAsync` as upstream has it (one read, counted as before); the three
new reads are the Request-as check and the administrator error shapes of the read and the edit. Keeping the lines by
dropping the Request-as check would loosen upstream's access rule. An unattended sync lands only added contract
lines, so both entries are `deferred` on the main line, with what they need: a maintainer's review of the side branch's
last commit. Accepted, that branch lands as it is (its ledger commit marks both `ported`). The rest of the contract
change only adds: the route `GET arr/requests/{requestId}/options` (`GetRequestOptions`, managers only, checked in the
body like the approve route) in `route-auth.snapshot.json`, `auth-helper-calls.snapshot.json`,
`auth-reads-by-route.base.json` and `baselines/inventory-routes.txt`, and `RouteAuthSnapshotTests.ExpectedRoutes` 228
to 229. The five Architecture tests failed with exactly these lines before the edit (`je12 test`, the port's tree) and
all 24 pass after; gate INV passes.

What it does, as upstream: `jellyseerr/user-status` (and the page-load bootstrap answer) gains `autoApprove`
(`movie`, `tv`, `movie4k`, `tv4k`) from the user's Seerr permissions; the movie, collection and series request dialogs
show "This request will be approved automatically." when it applies, a Tags field (a typeable multi-select of the
server's Radarr or Sonarr tags) and, for administrators, Request As; the Requests page has Approve with options on
pending requests for those who may approve, which opens the same options filled with what the request asks for
(`GET arr/requests/{requestId}/options`), then edits the request in Seerr and approves it. The Seerr group's dialog is
loaded on first use through a stand-in export, `JE.jellyseerrModal.ensureLoaded`.

Differences from upstream:

1. **Upstream's Approve with options never works.** Its edit body has no `mediaType`, which Seerr's request validator
   requires for that route, and for a request made without advanced options it sends a null server, profile, folder
   or language profile, which the validator also refuses; Seerr answers 400 every time, the dialog stays open with the
   toast "HTTP 400" and nothing is approved. The port sends the request's own type and leaves out a field that has no
   value either way. Filed as two found bugs (the missing `mediaType`; the null fields).
2. The options are checked for shape before Seerr is asked (whole numbers, a string folder, a list of whole-number
   tags); upstream forwards them, or fails with 500 on a non-numeric `userId`.
3. Request As never falls back to the first listed user: when the signed-in user's Seerr account (or a request's
   requester) is not in the list, nothing is chosen and no `userId` is sent.
4. Request As shows pictures from Jellyfin only; upstream falls back to the Seerr avatar at the Seerr host's address,
   a request from the browser to another host. The user entries keep only id, names and Jellyfin id.
5. A refused approval shows the server's message (escaped), not the error's text.
6. Approve with options follows the Requests page's rules for Approve: only for a request this account's list shows
   as pending with the right to approve, one approve in flight per request, nothing after a user switch.
7. The request dialogs read the options and build the note through imported functions, not the facade, so a replaced
   `JE.jellyseerrModal` keeps working; upstream's only test change adds the two facade stubs its dialogs need, which
   this tree's do not, so it is not applied.

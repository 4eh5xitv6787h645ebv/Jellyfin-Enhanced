## 2. The entry

### 95. Media Tags confirmations with the configuration page's own dialog

What upstream changed. The Media Tags tab asked with Jellyfin's `Dashboard.confirm`. That dialog adds a history entry and
goes back when it closes, and the router then builds the configuration page a second time: a copy without the page's
sidebar whose Media Tags tab stays on "Loading Media Tags settings…". Every confirmation in the tab went through it (Apply
defaults to all users, Rebuild cache, Reset all colours, the import, preset removal, Clear all browser caches), on Cancel
as well as OK. Upstream now asks with `JEAdmin.confirm`, the dialog the rest of the configuration page uses, and falls back
to Jellyfin's only when that page script is missing.

Here. The fault was the same: `client/src/features/media-tags/admin/admin-tags.ts` handed `askConfirm` (the dashboard's
dialog) to `page.ts`, whose `confirmAction` is what every section's `ctx.confirm` calls. The port adds upstream's
`askOnPage` beside it and hands that to the page instead; `JEAdmin` is read through a new `pageDialogs()` accessor in the
tab's host surface (`admin/host.ts`, typed with its `confirm` only), as the tab reads its other globals. As upstream: the
question goes to `JEAdmin.confirm` as text (that dialog escapes it except the few attribute-less formatting tags it
allows, and turns line breaks into `<br>`), an answer that throws or rejects counts as No, and the prompt shown after
leaving the page with unsaved edits (`leaveWithPending`) still asks with Jellyfin's dialog, since the configuration page
is no longer shown then. No differences from upstream.

Tests. Upstream's new test applies as is in `tests/frontend/features/media-tags/admin/features-admin-config-media-tags-tab.test.mjs`:
recorded failing on the tree before the port (`9d553490+dirty@e03f8c17`: no question reached `JEAdmin.confirm`) and
passing on `6be487cf` (`p95.tests.txt`).

Maintainerr's `GET /api/collections` embeds only a few members per collection (upstream's finding, its issue

`GET /api/collections/media/{id}/content/{page}?size=500` for every active collection.

| Upstream | Here | How |
|---|---|---|
| `Services/LeavingSoonService.cs`: `GetJsonAsync` (the guarded GET, taken out of `FetchMaintainerrAsync`), the paging loop, `ParseCollections`' third parameter | `Features/MediaTags/Services/LeavingSoonService.cs` | the hunks at the moved path (the guard is `Shared.Arr.ArrUrlGuard` here), then changed as below |
| no docs change | `docs/enhanced/tags.md`, `docs/advanced/api.md` | the paged requests and their failure rule are described |
| no test change | `tests/backend/Features/MediaTags/PosterTags/LeavingSoonTests.cs` | the fixture's paged route, three tests added, two expectations changed |

Kept from upstream: the guarded GET (address guard, key header, 30-second timeout, no redirect followed, 16 MiB),
the request and its page size, at most 40 pages, and the stop rule (`page × 500` reaches `totalSize`, or a page has
no rows; a short page is not the last one).

Differences from upstream:

1. **A failed page fails the refresh.** Upstream catches every failure of a collection's paging except a
   cancellation and carries on with the few embedded members, recording nothing. One failed page therefore takes
   the badge off every other member, as a successful refresh. Here only a 404 for a collection's first page (a
   Maintainerr without the route) falls back to the embedded members; any other failure is the refresh's failure,
   which keeps the previous answer and retries with the existing delays. Seen on the lab on both builds (section
   3). Filed as a found bug.
2. **An answer that is not a page is refused** (`not a Maintainerr collections answer`): anything but an object
   with an `items` array. Upstream reads it as a collection without members. Same entry.
3. **The paged members add to the embedded ones**; upstream replaces the embedded list. Maintainerr leaves a row
   out of a page when it cannot read that row's metadata from the media server (upstream's own comment in the
   commit), so with upstream's code a member the list itself names stops being one, and a page answered as
   `{"totalSize": 351, "items": []}` empties the collection. Here the port never reads fewer members than the
   list names. Filed as a found bug.
4. **An id that is not a number.** Upstream calls `TryGetInt32` on the collection's `id`, which throws for a
   string, outside its catch: one such collection fails the whole refresh (`request failed`) where the code
   before the commit read its embedded members. Here that collection keeps its embedded members and is not asked
   for pages; `totalSize` has the same guard. Filed as a found bug.
5. Only entries the parser recognises as collections are asked for pages, each id once. The list's unwrapping
   (`data`/`items`/`collections`/`results`) is one function, `CollectionList`, for the parser and the paging;
   upstream has it twice.
6. Docs: the two pages that describe the Maintainerr request now describe the paged one.
7. **Tests.** Upstream's commit has none, and its own `LeavingSoonTests` fail at `53ebf043` (9 of 47, run here in
   a checkout of that commit: its fixture answers the collections list on every path, which the new code reads as
   a collection without members). Filed as a found bug. Here the fixture gets the paged route
   (it answers 404 unless a test sets it) and three tests go through `RefreshAsync` against the fixture server:
   - 1,100 members over three pages with a short page, a collection answered without `totalSize`, an inactive one
     never asked for, ids that are missing or not numbers, the key and the base path on every request;
   - the pages adding to the embedded members, and the 404 fallback;
   - twelve ways a page can fail or not be one (HTTP 500, 404 after a first page, 401, a redirect, a slow answer,
     an array, an object without `items`, an empty body, HTML), each keeping the last good answer with its reason
     and reaching no other host; a `totalSize` that is not a number; a cancellation between pages.

   Two existing expectations change because a refresh now asks for pages too: the key test lists both requests
   where it had one, and the redirect test's "every request went to `/api/collections`" is a prefix check. The
   fixture's `Requests` counts the list requests (one per refresh attempt), so the refresh-count assertions stand
   as they were.

Kept from upstream as it is: members beyond 20,000 per collection are not read; a row that a page leaves out and
the list does not embed is not a member; when a page comes back without rows, the members the list does not embed
lose their badge until the next refresh (telling an unreachable media server from rows that are really gone needs
more than the answer holds).

## 6. Decisions made instead of asking

1. **Port 29 does not copy upstream's error handling.** REVIEW.md puts "a failure shown as nothing" third among
   the costly faults, and this service's own rule is that a part that fails keeps its previous answer. The four
   differences are in the ledger entry and filed as found bugs against upstream.
2. **The 404 fallback** is the one failure that stays a success, for a Maintainerr without the paged route (the
   case upstream's catch names), and only for a collection's first page.
3. **The union** (difference 3) instead of a new failure for "rows counted but none handed over": that answer
   also means a collection whose members are all gone from the media server, and refusing it would stop every
   collection's refresh until Maintainerr tidies up.
4. **A mocked Maintainerr.** The lab has none and may not reach one, so the lab check uses the lab's Sonarr mock
   with rules shaped after upstream's code and comment (`{totalSize, items}`, members by `mediaServerId`). What
   a real Maintainerr embeds in its list and how it pages was not seen by this run.
5. **Upstream's tests fail at its tip**, so a follow-up commit there is likely. None existed at 06:15; the next
   run will list it.

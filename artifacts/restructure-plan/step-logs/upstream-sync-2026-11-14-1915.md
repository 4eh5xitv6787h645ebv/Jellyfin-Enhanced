## 2. The entries

### 49 and 50. The scheduled Leaving soon refresh does nothing while nothing uses the data

Upstream's change: **Refresh Leaving Soon Tags** runs hourly; it used to reach the source (Maintainerr, or the
leaving collections) whenever the refresh interval had passed, even with every consumer off. Now it first asks
`LeavingSoonService.Consumed`: a source is set, and the badge default (`StatusTagsLeaving`), the home row or the
Maintainerr actions (both need a Maintainerr URL) use the facts, or, checked last because it reads every user's
`settings.json`, some user has the badge on. If not, the run writes one DEBUG line to the enhanced log and stops; a
run that goes ahead writes that it checked. The task's description says it runs only while something uses the data.

Re-implemented in the owning feature: `Features/MediaTags/Tasks/RefreshLeavingSoonTagsTask.cs` (namespace
`…ScheduledTasks` and key unchanged, so admins keep their schedules) and `Features/MediaTags/Services/LeavingSoonService.cs`.
The task takes `UserConfigurationManager` and `Logger`, both plugin singletons; `TagCacheLogos` already reads every
user's `settings.json` the same way for the logo tags. Differences from upstream:

- `Consumed` reuses `LeavingSoonSources.HomeRowWanted` and `MaintainerrActionsEnabled` (this tree's `Shared/MediaTags`),
  which are exactly upstream's two inline conditions.
- Tests: upstream's test of `Consumed` (in `tests/backend/Features/MediaTags/PosterTags/LeavingSoonTests.cs`) with two
  more cases, no configuration at all, and the users' settings not read when the configuration already decides; and a
  test on the real entry point, the task's `ExecuteAsync` over a `TagCacheService` and the loopback Maintainerr
  fixture: with a source nobody uses the run makes no request; after one user's settings turn the badge on, it makes
  one. That test failed before the port (`Expected: 0, Actual: 1`).
- Docs: `docs/enhanced/tags.md`, `docs/advanced/api.md` and `docs/advanced/project-structure.md` say the task does
  nothing while nothing uses the data. Upstream changed no docs.

Unchanged behaviour worth stating: removing the source still clears the facts, because a source change queues a
forced refresh (`QueueLeavingRefresh`), which does not go through the task; and a run that is skipped for days
refreshes on the first hourly run after something starts using the facts, because the stored next-refresh time has
long passed by then. A skipped run keeps the stored facts as they are; it changes nothing on disk.

Entry 50: `je12 regen` regenerated this tree's `tests/docs/production-inventory.json` in the same commit, with the
same change as upstream's bot commit: the task's `"settings.json"` literal, `storage_references` 96 to 97.
